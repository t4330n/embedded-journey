## 1. Board Selector로 만든 프로젝트에서 PA5 설정이 변경되지 않음

- **실습**: [01_led_blink](../01_gpio/01_led_blink)
- **증상**
  - STM32CubeMX의 **Board Selector**에서 `NUCLEO-C031C6`을 선택해 프로젝트를 생성함
  - PA5(LD4)를 `GPIO_Output`으로 바꾸려고 클릭해도 반응이 없고, `Pin PA5 is under BSP control` 툴팁만 표시됨
  - PA5, PC13, PA2, PA3 핀이 일반적인 회색·초록색이 아닌 **다홍색**으로 표시됨
- **원인**
  - 보드 단위로 프로젝트를 만들면 ST가 제공하는 **BSP(Board Support Package)** 가 보드의 LED·버튼·통신 핀을 미리 점유함
  - BSP가 관리하는 핀은 사용자가 Pinout 화면에서 직접 모드를 바꿀 수 없음
- **해결**
  - **MCU/MPU Selector**에서 칩(`STM32C031C6T6`)을 직접 선택해 프로젝트를 새로 생성
  - 빈 상태의 칩에서 PA5를 `GPIO_Output`으로 직접 설정하고 User Label `LD4`를 지정
- **배운 점**
  - Board Selector는 개발 보드로 빠르게 데모를 만들 때 편리하지만, 핀 설정을 BSP에 맡기게 된다.
  - 실무에서는 회사가 직접 설계한 보드를 사용하는 경우가 많으므로, **칩 단위로 핀을 직접 설정하는 방법**을 익혀 두는 것이 중요하다.

<br>

## 2. MCU 선택 시 부품 번호가 여러 개라 무엇을 골라야 할지 모름

- **실습**: [01_led_blink](../01_gpio/01_led_blink)
- **증상**
  - MCU/MPU Selector에서 `STM32C031C6`을 검색하자 `C6T3`, `C6T6`, `C6U6`, `C6T6TR` 등 여러 부품 번호가 표시됨
  - 보드에 실장된 칩이 어떤 것인지 구분하기 어려웠음
- **원인**
  - STM32 부품 번호는 **접미사마다 핀 수, 메모리 크기, 패키지, 동작 온도 범위**를 나타내며, 같은 칩이라도 조합에 따라 번호가 달라짐
- **해결**
  - 보드에 표기된 `LQFP48`과 보드 이름(`NUCLEO-C031C6`)을 근거로 **`STM32C031C6T6`** 선택
  - 부품 번호 `STM32C031C6T6` 해석

    | 글자 | 의미 |
    | :---: | --- |
    | `C` | 핀 수 48개 |
    | `6` | Flash 메모리 32KB |
    | `T` | LQFP 패키지 (칩 둘레로 핀이 나온 형태, `U`는 UFQFPN) |
    | `6` | 동작 온도 -40\~85℃ (`7`: -40\~105℃, `3`: -40\~125℃) |
    | `TR` | 칩은 동일하며, 생산용 테이프 & 릴 포장을 의미 |
- **배운 점**
  - 부품 번호의 각 글자에는 의미가 있으며, 이를 읽으면 **실제 하드웨어와 일치하는 칩**을 정확히 고를 수 있다.
  - 칩 선택은 이후 핀 배치와 설정 전체의 기준이 되므로, 보드 표기와 문서를 근거로 확인하는 습관이 필요하다.

<br>

## 3. SYS 메뉴에서 Debug(Serial Wire) 설정 항목을 찾을 수 없음

- **실습**: [01_led_blink](../01_gpio/01_led_blink)
- **증상**
  - 디버그 인터페이스를 켜기 위해 `System Core → SYS`를 열었으나 `Debug` 항목이 없고 `Timebase Source`만 표시됨
- **원인**
  - 참고한 안내는 다른 STM32 시리즈 기준이었고, **STM32C0 시리즈는 Debug 설정이 별도 메뉴에 있음**
  - STM32 시리즈마다 CubeMX의 메뉴 구성이 다를 수 있음
- **해결**
  - `Trace and Debug → DEBUG`에서 `Serial Wire` 활성화
  - PA13이 `SWDIO`, PA14가 `SWCLK`로 할당된 것을 Pinout 화면에서 확인
- **배운 점**
  - **SWD(Serial Wire Debug)** 는 디버거(보드의 ST-LINK)가 두 개의 선(SWDIO, SWCLK)으로 MCU에 코드를 쓰고 디버깅하는 방식이다. PC는 USB로 ST-LINK와 연결된다.
  - PA13, PA14는 리셋 직후 기본적으로 SWD로 동작한다. 하지만 CubeMX에서 Serial Wire로 명시해 두면 핀이 예약되어, 이후 다른 기능에 잘못 할당해 **디버그 연결이 끊기는 상황을 예방**할 수 있다.
  - 설정 위치가 안내와 다를 때는 시리즈별 차이를 의심하고 메뉴를 직접 확인해야 한다.

<br>

## 4. 코드 생성 시 프로젝트 폴더가 이중으로 생성될 뻔함

- **실습**: [01_led_blink](../01_gpio/01_led_blink)
- **증상**
  - Project Manager에서 `Project Location`을 `.../01_gpio/01_led_blink`로 지정하자
    `Toolchain Folder Location`이 `.../01_led_blink/01_led_blink/`로 표시됨
- **원인**
  - CubeMX는 **`Project Location` + `Project Name`** 경로에 프로젝트 폴더를 새로 생성함
  - 위치에 프로젝트 이름까지 포함하면 같은 이름의 폴더가 한 번 더 만들어짐
- **해결**
  - `Project Location`을 상위 폴더인 `.../embedded-journey/01_gpio`로 변경
  - `Toolchain Folder Location`이 `.../01_gpio/01_led_blink/`로 바뀐 것을 확인한 뒤 코드 생성
- **배운 점**
  - 코드 생성 전 **최종 생성 경로(Toolchain Folder Location)를 확인**하는 습관이 필요하다.
  - 레포 폴더 구조를 일정하게 유지해야 실습 기록과 프로젝트 파일을 함께 관리하기 쉽다.

## 5. HAL 내부의 비트 연산이 왜 필요한지 이해되지 않음

- **실습**: [01_led_blink](../01_gpio/01_led_blink)
- **증상**
  - `HAL_GPIO_TogglePin` 내부 코드를 열어 보았으나, 아래 한 줄에서 `&`, `~`, `<<`, `|` 연산을 **왜** 하는지 이해할 수 없었음
    ```c
    GPIOx->BSRR = ((odr & GPIO_Pin) << GPIO_NUMBER) | (~odr & GPIO_Pin);
    ```
  - 코드를 문법적으로 읽을 수는 있었지만, ODR·BSRR이 무엇인지 설명을 읽어도 개념이 와닿지 않았음
- **원인**
  - ODR, BSRR 같은 **GPIO 레지스터가 실제 하드웨어와 어떻게 연결되는지** 모른 채 코드만 읽었음
  - 레지스터를 일반 변수(메모리)처럼 생각해, 값을 쓰는 것이 왜 핀 동작으로 이어지는지 연결하지 못했음
- **해결**
  - 토글 코드에 브레이크포인트를 걸고 디버그 모드로 실행한 뒤, **SFRs 창**에서 `GPIOA → ODR`을 관찰
  - 한 단계씩 실행하며 `OD5` 비트가 0 ↔ 1로 바뀔 때 LD4가 함께 꺼지고 켜지는 것을 확인 (`GPIOA_ODR`: `0x0` ↔ `0x20`)
  - 이후 `GPIOA->ODR ^= (1U << 5)`와 BSRR을 이용한 토글을 직접 구현하며 HAL 연산의 의미를 이해함

    | 연산 | 의미 |
    | --- | --- |
    | `odr & GPIO_Pin` | 현재 켜져 있는 대상 핀만 추출 |
    | `<< 16` | BSRR의 Reset 영역(16~31번)으로 이동 → 끄기 요청 |
    | `~odr & GPIO_Pin` | 현재 꺼져 있는 대상 핀만 추출 → Set 영역 켜기 요청 |
    | `\|` | 두 요청을 합쳐 BSRR에 한 번에 기록 |
- **배운 점**
  - 레지스터는 칩 내부의 고정된 주소에 연결된 하드웨어 제어용 칸이며, 값을 쓰면 실제 핀 출력이 바뀐다. (`GPIOA_ODR` 주소 `0x50000014` = GPIOA 시작 주소 `0x50000000` + `0x14`)
  - 코드만 읽어서 이해되지 않는 개념은 **디버거로 레지스터 값과 실제 동작을 함께 관찰**하면 빠르게 이해할 수 있다.
  - 라이브러리 내부를 직접 열어 보고 같은 동작을 레지스터로 다시 구현해 보면, 라이브러리가 하는 일을 정확히 알 수 있다.

<br>

## 6. BSRR에 쓴 비트 값이 계속 유지된다고 오해함

- **실습**: [01_led_blink](../01_gpio/01_led_blink)
- **증상**
  - `GPIOA->BSRR = (1U << 21);`을 실행하면 BSRR의 21번 비트가 계속 1로 남고, `(1U << 5)`를 쓰면 5번 비트도 계속 1로 남는다고 생각함
  - BSRR의 비트와 ODR의 비트를 같은 것으로 혼동해, "21번 비트를 1로 하면 5번 비트가 0이 되는 것인지" 헷갈림
- **원인**
  - **BSRR은 값을 저장하지 않는 쓰기 전용 레지스터**로, 쓴 값은 ODR을 변경하는 요청으로만 동작함
  - 핀의 실제 출력 상태는 **ODR**에 저장되며, BSRR을 읽으면 항상 0이 반환됨
- **해결**
  - SFRs 창에서 `GPIOA_BSRR`과 `GPIOA_ODR`을 함께 펼쳐 놓고 한 단계씩 실행
  - LED가 켜질 때도 꺼질 때도 `GPIOA_BSRR`은 항상 `0x0`이고, `GPIOA_ODR`만 `0x0` ↔ `0x20`으로 바뀌는 것을 확인

    | 쓴 값 | BSRR을 읽으면 | ODR 5번 비트 | LD4 |
    | --- | :---: | :---: | :---: |
    | `BSRR = (1U << 5)` | `0x0` | 1 | 켜짐 |
    | `BSRR = (1U << 21)` | `0x0` | 0 | 꺼짐 |
- **배운 점**
  - BSRR의 하위 16비트(0\~15번)는 Set(켜기), 상위 16비트(16\~31번)는 Reset(끄기) 요청이며, 1을 쓴 비트에 해당하는 ODR 비트만 바뀐다.
  - 현재 핀 상태를 판단할 때는 값을 기억하지 않는 BSRR이 아니라 **ODR**을 읽어야 한다.
  - 레지스터마다 읽기/쓰기 특성(RW, 쓰기 전용 등)이 다르므로, 값을 해석하기 전에 그 레지스터의 성격을 먼저 확인해야 한다.

## 7. 버튼을 눌렀을 때 LED가 예상과 반대로 동작함

- **실습**: [02_button_led](../01_gpio/02_button_led)
- **증상**
  - "버튼을 누르면 입력이 1이 된다"고 가정하고 아래와 같이 작성함
    ```c
    if (HAL_GPIO_ReadPin(B1_GPIO_Port, B1_Pin) == GPIO_PIN_SET) {
        HAL_GPIO_WritePin(LD4_GPIO_Port, LD4_Pin, GPIO_PIN_SET);
    } else {
        HAL_GPIO_WritePin(LD4_GPIO_Port, LD4_Pin, GPIO_PIN_RESET);
    }
    ```
  - 실행하자마자 LD4가 켜져 있고, 버튼을 누르면 꺼지며, 떼면 다시 켜짐 (의도와 정반대)
- **원인**
  - NUCLEO-C031C6의 사용자 버튼 B1(PC13)은 **풀업 회로**로 연결되어 있어, 누르지 않으면 1, 누르면 0이 읽힘 (**액티브 로우**)
  - 버튼의 입력 값은 회로 설계에 따라 정해지는데, 회로를 확인하지 않고 "눌림 = 1"이라고 가정함
- **해결**
  - 디버거 SFRs 창에서 `GPIOC_IDR`을 확인: 버튼을 뗐을 때 `0x2000`(13번 비트 = 1), 눌렀을 때 `0x0`(13번 비트 = 0)
  - 한 단계씩 실행하며, IDR이 `0x0`일 때 켜기 코드로, `0x2000`일 때 끄기 코드로 진행하는 것을 확인
  - `GPIOC_PUPDR = 0x0`으로 칩 내부 풀업·풀다운이 꺼져 있는데도 평소 1이 안정적으로 읽히는 것을 보고, 보드에 외부 풀업 회로가 있음을 확인
  - 조건을 `GPIO_PIN_RESET`으로 바꾸고, 의미가 드러나도록 `B1_PRESSED`로 이름을 붙임
    ```c
    #define B1_PRESSED  GPIO_PIN_RESET   // B1은 액티브 로우: 누르면 0

    if (HAL_GPIO_ReadPin(B1_GPIO_Port, B1_Pin) == B1_PRESSED) { ... }
    ```
- **배운 점**
  - 입력 핀의 값은 **회로(풀업/풀다운)에 따라** 정해지므로, 코드를 작성하기 전에 회로도나 디버거로 실제 값을 먼저 확인해야 한다.
  - 풀업은 평소 1·누르면 0, 풀다운은 평소 0·누르면 1이며, 보드에 외부 저항이 있으면 소프트웨어에서는 No pull로 설정해야 두 저항이 충돌하지 않는다.
  - 회로의 특성은 `B1_PRESSED`처럼 이름으로 감추면 코드의 의도가 분명해지고, 회로가 바뀌어도 한 곳만 수정하면 된다.

<br>

## 8. 실험에 사용할 A0 핀의 위치를 찾지 못함

- **실습**: [기초 02 플로팅 입력](../00_basics/02_floating_input)
- **증상**
  - 플로팅 실험에 PA0를 쓰기로 했지만, 보드에서 해당 핀이 어디인지 알 수 없었음
  - 위치를 "보드 왼쪽 아래"로 안내받았으나, 보드를 놓은 방향에 따라 실제로는 위쪽에 있어 헷갈림
- **원인**
  - 보드의 커넥터에는 칩 핀 이름(PA0)이 아니라 **아두이노 핀 이름(A0)** 이 인쇄되어 있음
  - "왼쪽·아래" 같은 방향 표현은 보드를 놓은 방향에 따라 달라짐
- **해결**
  - 보드 사용자 매뉴얼(UM2953)의 ARDUINO 커넥터 핀 배치 표에서 **A0 = PA0 (CN8 1번 핀)** 임을 확인
  - 보드 사진에 A0, 3V3, GND 위치를 표시하고, 방향이 아닌 **보드에 인쇄된 `A0` 글씨**를 기준으로 위치를 찾음
- **배운 점**
  - 보드에 적힌 이름(A0, D13 등)과 칩의 핀 이름(PA0, PA5 등)은 다를 수 있으므로, 보드 사용자 매뉴얼의 **핀 매핑 표**를 확인해야 한다.
  - 핀 위치는 방향보다 **보드의 인쇄 글씨(실크 인쇄)** 를 기준으로 찾는 것이 정확하다.

## 9. 버튼을 누르면 입력 변수 값이 저절로 바뀐다고 오해함

- **실습**: [03_button_toggle](../01_gpio/03_button_toggle)
- **증상**
  - 버튼을 누르면 입력을 담는 변수가 바로 0으로, 다시 누르면 1로 **저절로 바뀔 것**이라고 생각함
  - 디버거에서 Step Over로 한 줄씩 실행해 보니, 버튼을 눌러도 변수 값은 그대로이고 `Read_Input()` 줄을 지날 때만 바뀜
- **원인**
  - 칩은 버튼을 계속 지켜보지 않고, **입력을 읽는 코드가 실행되는 순간에만** IDR에서 핀 값을 가져옴 (폴링)
  - Run으로 실행하면 `while` 루프가 매우 빠르게 반복되어, 누르는 즉시 값이 바뀌는 것처럼 보였을 뿐임
- **해결**
  - 입력을 매 루프마다 읽고, **이전 값(`prev_state`)과 현재 값(`now_state`)을 비교**해 1 → 0으로 바뀐 순간에만 토글하도록 작성
- **배운 점**
  - 변수는 코드가 값을 넣을 때만 바뀐다. 입력 값은 "읽는 순간의 핀 상태"다.
  - 버튼이 눌렸을 때 칩이 하던 일을 멈추고 바로 알려 받는 방식은 **인터럽트(EXTI)** 이며, 이후 단계에서 다룬다.

<br>

## 10. 점퍼선으로 한 번 연결해도 눌림 횟수가 10 이상 증가함

- **실습**: [03_button_toggle](../01_gpio/03_button_toggle)
- **증상**
  - 디바운싱 없이 B1을 10번 누르면 `press_count`가 정확히 **10**이었음
  - 같은 코드로 A0(PA0, 내부 풀업)에 꽂은 점퍼선을 GND에 꽂았다 빼면, 한 번에 10 이상씩 올라 **131**이 됨
  - LED가 꽂을 때 바뀌지 않거나, 코드상 바뀌면 안 되는 **뺄 때** 바뀌기도 함
- **처음 추측**
  - 조건문 안의 `press_count++`와 토글은 함께 실행되므로, LED가 그대로라면 LD4 회로 중간의 **트랜지스터(T2)** 에 문제가 있다고 추측함
- **원인**
  - 금속 접점이 붙거나 떨어지는 순간 여러 번 붙었다 떨어지는 **바운싱**이 일어나, 1 → 0 변화가 여러 번 읽힘
  - 토글이 짝수 번 일어나면 LED가 원래 상태로 돌아가 바뀌지 않은 것처럼 보이고, 뗄 때의 떨림 속에 섞인 1 → 0 때문에 뺄 때 바뀌기도 함
  - 트랜지스터는 PA5 출력에 따라 LED 전류 길을 열고 닫을 뿐이며 문제가 없었음
  - B1은 회로에 **C16(100nF)·R26(100Ω)** 이 있어 전압 변화가 부드럽고, 스위치용 부품이라 이번 측정에서는 떨림이 관찰되지 않음
- **해결**
  - 디버거의 **Live Expressions**로 `press_count`를 실시간으로 보며, 같은 동작을 10번 했을 때의 횟수를 측정해 원인을 확인
  - 값이 **20ms 동안 유지될 때만 인정**하는 소프트웨어 디바운싱 적용
    - 방법 1: 1 → 0을 보면 `HAL_Delay(20)` 후 다시 확인 → 10
    - 방법 2: `HAL_GetTick()`으로 마지막 변화 후 20ms가 지났는지 비교 → 10
- **배운 점**
  - 기계식 버튼·스위치 입력에는 바운싱이 있으므로, 회로(RC 필터)나 코드(디바운싱)로 걸러야 한다.
  - 원인을 추측만 하지 않고 **횟수를 측정**하자 문제가 회로가 아닌 입력 떨림이라는 것을 바로 알 수 있었다.
  - `HAL_Delay`는 기다리는 동안 CPU가 멈추므로, 실제 펌웨어에서는 시간 비교 방식(논블로킹)을 주로 쓴다.

<br>

## 11. Run으로 실행하면 Live Expressions에서 변수 값을 볼 수 없음

- **실습**: [03_button_toggle](../01_gpio/03_button_toggle)
- **증상**
  - 버튼을 누를 때 `press_count`가 바뀌는 모습을 보려고 툴바의 **Run**(초록색 원형 ▶)으로 보드에 올렸으나, 디버거 창의 값을 볼 수 없었음
  - 디버그 모드의 **Expressions** 창은 Step Over로 멈췄을 때만 값이 바뀌어, 실행 중의 변화를 볼 수 없었음
- **원인**
  - **Run**은 프로그램을 보드에 올린 뒤 **디버거 연결 없이** 실행하는 버튼임
  - **Expressions** 창은 프로그램이 멈춘 시점의 값만 보여 주며, 실행 중 값을 계속 읽어 오는 창은 **Live Expressions**임
- **해결**
  - **Debug**로 시작해 `main()`에서 멈춘 뒤, **Resume(F8)** 으로 실행을 이어 감 (Debug 창에 `Running` 표시)
  - **Live Expressions**(L 탭)에 `press_count`를 추가해, 프로그램을 멈추지 않고 실시간으로 값을 확인
- **배운 점**
  - Run은 디버거 없이 실행, Debug + Resume은 디버거를 연결한 채 실행이다.
  - 빠르게 일어나는 현상은 Step Over로 멈춰 가며 보기보다, Live Expressions로 **실행 중에 관찰**해야 한다.

## 12. CPU가 바쁠 때 폴링으로 짧게 누른 버튼을 놓침

- **실습**: [01_exti_button](../02_timer_interrupt/01_exti_button)
- **증상**
  - `while` 안에 `HAL_Delay(2000)`을 넣어 CPU를 바쁘게 만든 뒤 폴링으로 B1을 짧게 10번 누르자, `press_count`가 **1**만 증가함
  - 버튼을 3초 이상 누르고 있으면 바뀌긴 했지만, `HAL_Delay`가 끝난 뒤에야 반응함
- **처음 생각**
  - `while` 안의 읽기 코드가 너무 빠르게 지나가서, 그 순간에 맞춰 누르기 어렵다고 생각함
- **원인**
  - 읽기 코드가 빠르게 끝나는 것도 맞지만, 핵심은 **다음 읽기까지 2초의 빈틈**이 있다는 점임
  - 약 0.2초짜리 누름이 이 빈틈 안에서 시작하고 끝나면 한 번도 읽히지 않음 (0.2초 ÷ 2초 ≈ 10번 중 1번)
- **해결**
  - PC13을 `GPIO_EXTI13`(Falling edge)으로 설정하고 NVIC에서 `EXTI line 4 to 15`를 켬
  - `HAL_GPIO_EXTI_Falling_Callback`에서 LED를 토글하도록 변경 → CPU가 `HAL_Delay` 중이어도 누를 때마다 바로 반응
- **배운 점**
  - 폴링은 CPU가 다른 일을 하는 동안 입력을 확인할 수 없어, 짧은 입력을 놓치거나 반응이 늦어진다.
  - 반응 속도가 중요하거나 CPU가 다른 일로 바쁜 시스템에서는 인터럽트를 사용한다.

<br>

## 13. 인터럽트는 값이 바뀐 것을 언제 어떻게 확인하는지 이해되지 않음

- **실습**: [01_exti_button](../02_timer_interrupt/01_exti_button)
- **증상**
  - 폴링은 `while`에서 계속 확인하는데, 인터럽트도 결국 값이 바뀐 것을 누군가 확인해야 할 것 같아 **확인하는 주기가 따로 있는지** 이해되지 않음
  - 디버거에서 `EXTI_FPR1`이 `0x2000` → `0x0`으로 바뀌는 것을 봤지만, 처음에는 이것이 버튼 값의 1 → 0과 같은 것이라고 생각함
- **원인**
  - 인터럽트에서 입력 변화를 확인하는 것은 코드가 아니라 **EXTI 회로**(항상 핀을 감시)와 **CPU 하드웨어**(명령어마다 인터럽트 요청 확인)임
  - `FPR1`은 버튼 값이 아니라 "Falling이 일어났다"는 **깃발**이며, 하드웨어가 올리고 HAL이 지움
- **해결**
  - 버튼을 누른 순간부터 콜백 실행·복귀까지를 8단계로 나눈 흐름도와 [학습용 시뮬레이션](https://t4330n.github.io/embedded-journey/02_timer_interrupt/01_exti_button/sim/interrupt-flow.html)(AI의 도움을 받아 제작)으로 정리
  - `EXTI4_15_IRQHandler`에 브레이크포인트를 걸어 호출 순서(`HAL_Delay` 도중 `<signal handler called>`)와 `FPR1` 깃발이 올라갔다 내려가는 것을 확인
- **배운 점**
  - 폴링은 소프트웨어가 알아채고, 인터럽트는 하드웨어가 알아채서 소프트웨어(콜백)를 불러 준다.
  - 깃발을 지우지 않으면 핸들러가 끝없이 다시 실행되므로, HAL은 콜백을 부르기 전에 깃발부터 지운다.
